# 方案设计模板

> 用途：为 `docs/solutions/` 下的方案文档提供统一骨架。
>
> **分档使用，不要照抄全部章节。** 先判断方案规模，再决定写到哪一档：
>
> - **轻量档（默认）**：单模块或单链路改动、行为基本可预测。只写标有 `[核心]` 的节即可：背景与约束、目标、User Stories、解决方案、关键流程、改动清单、验收、风险、任务管理。仓库里多数方案属于这一档（80 至 150 行）。
> - **完整档**：跨模块、涉及 Ent schema / GraphQL / 数据库 migration / 异步任务 / 并发状态机时，按需追加标 `[按需]` 的节（模型设计、ERD、Migration、上线后验证）。纯网关透传或单点修复不需要为了“完整”强行补齐。
>
> 两档只区分方案规模。**每份交付方案都必须可执行**，不以「草案」或「后续确认」代替尚未完成的关键决策；实际改代码、生成代码、迁移或发布仍按用户授权和 `.agent/rules/` 执行。
>
> 标题中英不限，与同目录既有方案文档保持一致即可。

## 写作原则

1. **先说为什么，再说怎么做**：背景要解释真实问题，不能直接跳到实现。
2. **目标可验收**：目标必须能被测试、观察或人工确认；不要写「提升体验」「优化质量」这种无法闭环的表述。
3. **方案有取舍**：比较真正合理的备选方案，说明选择依据。没有实质备选时说明原因，不为填表编造一个明显更差的方案。
4. **实施可交接**：另一个工程师只读本文，应能知道改哪些模块、按什么顺序做、怎么验证。
5. **风险不藏起来**：无法第一版解决的问题放进「已知妥协」，不要伪装成已解决。
6. **交付前解决实施阻塞**：关键选型、对外 API 契约、生成代码流程和模块边界必须在方案交付前明确。尚有阻塞时如实报告未完成项，不能仅列出负责人或改标「草案」就把方案视为完成。最终方案不留 TBD、TODO 或「实现时再决定」；不影响当前交付的取舍写入「已知妥协」。
7. **各节各司其职**：目标说明要达到的结果，实施说明怎么做，验收说明通过条件，上线后验证观察实际运行。相同定义和指标只维护一处，其他章节引用，不重复堆叠。

## 1. 背景 `[核心]`

说明这个方案为什么存在。

建议包含：

- 当前系统怎么工作。
- 触发问题的真实场景。
- 现有方案为什么不够。
- 问题影响范围：请求链路、数据、性能、兼容性、维护成本、产品能力。
- 已知约束：对外 API 兼容、数据库方言、已有规则、不可改边界。

### 现状

用 3-5 条事实描述当前实现，不要评价。

事实以当前代码或实际操作为依据，标明关键文件、函数、调用关系或验证记录；未运行的行为不能写成已验证。涉及已有方案或用户决策时，说明本次沿用、替代的内容及依据，有冲突先解决。不要把旧方案当成已经实现的现状，也不要把作者建议写成用户已确认的要求。

```text
- `internal/server/...` 中 ... 的调用链是 ...
- `llm/pipeline/...` 当前按 ... 处理 ...
- 线上/测试观察到 ...
```

### 问题

按问题分组写清症状、根因、影响。

```text
问题：
- 症状：
- 根因：
- 影响：
```

### 约束

列出会影响方案选择的硬约束，例如：

- 对外 OpenAI / Anthropic 兼容接口的请求、响应和错误格式不能被破坏。
- 必须兼容 PostgreSQL、MySQL/TiDB、SQLite（除非明确限定为方言专属能力）。
- `llm/` 是独立 Go module，跨模块改动必须在两个模块分别可编译、可测试。
- 不能破坏已有缓存结构；修改序列化形状需版本化 key 或读取兜底，见 `.agent/rules/cache-compat.md`。
- 修改 Ent schema 或 GraphQL schema 后必须走 `make generate`，不手写常规 schema migration SQL。
- 不能引入新的、未确认的运行时依赖或外部服务。

## 2. 目标 `[核心]`

目标回答「做到什么算成功」。

### 目标

写可验证目标：

1. ...
2. ...
3. ...

### 非目标

明确本方案不解决什么，防止范围膨胀：

1. ...
2. ...
3. ...

### 成功信号

用可观察信号描述目标达成：

| 信号 | 验证方式 |
|------|----------|
| ... | 单测 / 集成测试 / E2E / 手动检查 / 数据观察 |

## 3. User Stories `[核心]`

从 API 使用方、控制台用户、运维/管理员和系统维护者角度写。不要只写功能列表。

AxonHub 常见角色：

- **API 使用方**：通过 OpenAI / Anthropic 兼容接口调用模型的客户端或 SDK。
- **控制台用户**：在 `frontend/` 中配置 channel、API key、模型、用量等资源的操作者。
- **运维 / 管理员**：关注升级、迁移、限流、故障切换和可观测性的人。
- **维护者**：后续修改该模块的开发者。

格式：

```text
作为 {角色}，
我希望 {能力 / 行为}，
以便 {价值 / 避免的问题}。
```

建议至少覆盖：

- 核心调用路径（请求如何进入、如何路由、返回什么）。
- 错误 / 限流 / 超时 / 回滚路径。
- 旧数据、旧配置或旧 API 行为的兼容路径。
- 开发与维护路径，如果方案引入新抽象、新数据模型或新的 transformer / pipeline 阶段。

示例：

1. 作为 API 使用方，我希望继续用原有 OpenAI 请求格式调用新增的模型供应商，以便不修改客户端代码即可切换后端。
2. 作为控制台用户，我希望在 channel 配置中看到新增参数及其校验错误，以便在保存前发现配置问题。
3. 作为维护者，我希望请求转换逻辑集中在 `llm/transformer/` 的明确入口，以便排查不同供应商的行为差异。

## 4. 解决方案 `[核心]`

本节先说明合理选择及取舍，再给出明确决策。只有一种合理做法时说明依据即可，不强行填满方案对比表。

### 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A | ... | ... | ... | 推荐 / 放弃 |
| B | ... | ... | ... | 推荐 / 放弃 |
| C | ... | ... | ... | 推荐 / 放弃 |

表格行数按实际选择保留。备选必须能满足基本目标，比较其真实代价与限制，不能用明显违反需求的做法充数。

### 决策

推荐方案：...

选择理由：

1. ...
2. ...
3. ...

拒绝方案：

- 方案 X：为什么不选。
- 方案 Y：为什么不选。

### 核心原则

列出实施时不能违背的原则，通常 3-5 条。

1. ...
2. ...
3. ...

### 关键假设

写出方案成立依赖的前提。

| 假设 | 如果不成立 | 应对 |
|------|------------|------|
| ... | ... | ... |

## 5. 方案实施

本节要让实现者知道「改什么、怎么改、按什么顺序改」。

### 5.1 模型设计 `[按需]`

如果涉及数据或领域对象，先定义模型。Ent schema 的实际字段、边和索引以 `internal/ent/schema/*.go` 为准，本节只说明语义和取舍，不复制整份 schema。

```text
entity_name
- id
- field_a
- field_b
- status: active / archived
- created_at
- updated_at
```

说明：

- 字段语义。
- 唯一约束和业务不变量。
- 状态机与生命周期。
- 关系及删除/归档行为（`OnDelete` 策略）。
- 是否冗余派生字段；如果冗余，为什么值得。
- 索引设计理由；只列查询形状和取舍，不在文档维护索引清单（见 `.agent/rules/database-indexes.md`）。

### 5.2 ERD `[按需]`

涉及多表或多对象关系时必须画。

```text
Channel
  |
  | 1:N
  v
ChannelModelPrice ---- N:1 ---- Model
  |
  | 1:N
  v
ChannelModelPriceVersion
```

说明每条关系的删除、归档、级联策略。

### 5.3 关键业务流程 `[核心]`

非平凡改动必写。用步骤或序列图说明最重要的流程，至少覆盖 happy path 和失败路径。

写清系统实际读取、校验、转换、保存和返回什么；不能只有 `Handler → Biz → Ent` 的空泛分层。涉及请求转换时，标出 pipeline 中生效的 stage 和 transformer。

```text
1. 客户端以 OpenAI 格式请求 ...
2. Handler 解析并鉴权 ...
3. Pipeline 选择 channel / model，outbound transformer 转为供应商格式 ...
4. 供应商返回后，inbound transformer 转回统一格式 ...
5. 记录 usage / request / trace，并返回客户端 ...
```

失败路径至少说明：

- 无可用 channel、模型映射失败、供应商超时或限流时如何返回。
- 是否需要重试、降级或切换 channel。
- 部分写入（usage、trace、request body）失败时的一致性处理。

复杂流程用图：

```text
Client -> Handler -> Biz -> Transformer -> Provider
  |         |         |          |            |
  |         |         |          |            +-- response
  |         |         |          +--------------- transform
  |         |         +-------------------------- select channel
  |         +------------------------------------ auth / parse
  +---------------------------------------------- render error
```

### 5.4 改动清单 `[核心]`

**默认按文件分小节写**，每个文件下用要点列出「在哪个函数 / 类型、加什么、为什么」。这是可交接性最高的写法，不要压成一行表格。

```markdown
#### `internal/server/biz/foo.go`
- `FooService.Bar()`：新增 X 参数，原因 ...
- 新增字段 `baz`：用于 ...

#### `llm/transformer/openai/foo.go`
- `FooTransformer.TransformRequest()`：兼容 ...，原因 ...
```

涉及 Ent / GraphQL 时：

- 列出 `internal/ent/schema/*.go`、`internal/server/gql/*.graphql` 与 `gqlgen.yml` 的改动。
- 明确需要执行 `make generate`，并说明生成后需要手写实现的 resolver 方法。
- GraphQL 字段改动要覆盖完整链路：schema → 生成代码 → 前端 query/mutation → 表单提交与回显。

涉及前端用户可见文案时，改动清单要包含 i18n 两个文件：`frontend/src/locales/en/<module>.json` 与 `frontend/src/locales/zh-CN/<module>.json`，key 必须一致（见 `.agent/rules/frontend-i18n.md`）。

文件很多时，纯一句话能说清的改动也可用表格补充：

| 模块 / 文件 | 改动 | 原因 |
|-------------|------|------|
| `internal/...` | ... | ... |

### 5.5 Migration `[按需]`

涉及 Ent schema、索引、配置格式、缓存结构或历史数据时必须写。

常规 schema 变更遵循 `.agent/rules/ent-graphql.md`：修改 `internal/ent/schema/`，执行 `make generate`，由 Ent-managed migration 处理，不手写 SQL。索引变更还要遵循 `.agent/rules/database-indexes.md`。需要一次性补数据或修复历史数据时，放到 `internal/ent/migrate/datamigrate/`。

本节至少说明：

- schema 如何变化，是否需要 `make generate`。
- 旧数据如何迁移或回填；迁移是否幂等。
- 默认值、空值和历史记录如何解释。
- 回滚是否可能；失败如何处理。
- 是否需要 `internal/ent/migrate/migrations/` 下的特殊 SQL（仅限 Ent 无法表达的场景）。
- 多方言验证方式，以及是否需要跑升级路径测试。

```text
from 旧版本 to 新版本:
1. 修改 Ent schema 并执行 make generate
2. 通过 datamigrate 回填 ...
3. 校验 ...
4. 运行 make migration-test-all-dbs TAG=<旧版本>
```

### 5.6 上线后验证 `[按需]`

本次改动存在需要在实际使用中确认的可靠性风险时写，例如异步任务恢复、流式响应中断、请求落盘、GC 或长时间运行的 worker。纯确定性改动可由第 6 节验收覆盖。

说明哪些现象需要关注、从哪里取得证据、出现问题后如何处理。优先使用已有请求记录、usage log、trace 和结构化日志（zap），不为填满本节新增监控系统。

| 本次改动的风险 | 观察证据 | 异常判断依据 | 检查时机与处理 |
|----------------|----------|--------------|----------------|
| 例如，异步任务显示成功但结果不可读 | 请求记录、worker 日志、实际产物 | 产物无法读取，或状态与实际结果不一致 | 出现问题时按 trace/request ID 复现，检查状态流转与落盘步骤 |

## 6. 验收标准 `[核心]`

验收标准要覆盖功能、兼容、错误、性能或质量。

| 类别 | 标准 | 验证方式 |
|------|------|----------|
| 功能 | ... | ... |
| 对外兼容 | ... | ... |
| 错误处理 | ... | ... |
| 性能 | ... | ... |
| 可维护性 | ... | ... |

规则：

- 每条标准都要能判断 pass / fail。
- 不要写「体验更好」；写「某操作在 N 步内完成」「错误提示包含可操作原因」。
- 修改了哪些模块，就写对应测试命令：
  - 根模块：`go test ./...`
  - `llm/` 模块：`cd llm && go test ./...`
  - 前端单测：`cd frontend && npm run test:unit`
  - 全链路 / UI 行为：`make e2e-test`
  - 升级路径：`make migration-test-all-dbs TAG=<旧版本>`
- 涉及对外接口时，验收要包含真实 OpenAI / Anthropic 客户端或契约测试，而不只是内部单测。

## 7. 风险 `[核心]`

风险要写具体触发条件和应对。

| 风险 | 触发条件 | 影响 | 对策 |
|------|----------|------|------|
| ... | ... | ... | ... |

常见风险角度：

- 数据库 migration 失败或多方言行为不一致。
- 对外 API 契约 / 请求转换兼容破坏。
- 缓存结构或 key 不兼容。
- 并发、重入、重复计费或 usage 重复写入。
- 状态不同步（请求状态、task 状态、channel 状态）。
- 性能退化（额外查询、序列化、全量加载）。
- 供应商超时、限流、错误格式差异。
- 前端 GraphQL 字段链路漏改导致提交或回显失败。

## 8. 已知妥协 `[按需]`

这里写第一版接受但不能假装不存在的问题。

每条妥协要说明：

- 为什么第一版不解决。
- 会造成什么影响。
- 什么时候需要升级。
- 后续可能怎么做。

格式：

```text
1. 妥协：
   - 原因：
   - 影响：
   - 升级触发：
   - 后续方向：
```

## 9. 任务管理 `[核心]`

每个方案只维护一张任务表，不另写任务详情。单文件方案放在正文末尾、本节所在位置；多文档方案放在总览 README 末尾，分篇只链接该表。方案正文保存需求、设计和验收标准，任务表保存执行进度。

| ID | 任务 | 状态 | 依赖 | 当前记录 |
|----|------|------|------|----------|
| T-01 | [可独立验收的交付结果](#6-验收标准-核心) | 待核对 | 无 | 核对当前入口、调用链和已有验收记录 |
| T-02 | [另一项交付结果](#6-验收标准-核心) | 待办 | T-01 | 已确认的具体缺口 |

- 一个任务对应一个可验收结果，包含实现及必要验证；任务名称链接正文中的需求与验收标准，不复制设计或另建详情。部分已实现、部分未实现时拆分任务，不写百分比。
- 状态统一为：**待核对**（尚未确认实际差距）、**待办**（已确认缺口）、**进行中**（正在实施）、**待验收**（实现已接通，必要验证未齐）、**完成**（完成条件及必要验收有证据）、**已取消**（明确不再执行）。缺少决策或外部条件时，在当前记录写明阻塞，不另增状态列。
- 未完成任务的当前记录写剩余工作或阻塞，必要时链接已核对的实现；完成后替换为交付结果、实现位置和验收证据，不保留剩余事项。若仍有任务范围内的工作，不能标完成；新增需求另建任务。取消时写原因或替代任务 ID。
- 证据只写实际核对或执行的内容：代码位置、提交、验证命令与结果、平台及日期。存在代码或测试文件不等于验收通过；未运行、跳过或未覆盖的数据库方言必须明确，不重复要求已具备有效证据的验证。
- 表前注明核对日期、分支与提交，以及影响判断的未提交改动。代码或需求变化后，按影响更新相关行；不要将旧版本验证结果当作当前版本保证，也不要无依据重置其他任务状态。
- 开始执行前对照关联任务与当前代码；修改关联代码后、向用户报告前，同步更新该行。中断时留下具体停点，不能只写“进行中”。
- 页首、导航表、依赖图和分篇不再重复写“已完成”“下一步”等进度。

多任务依赖复杂时可以保留依赖图，但图中只写任务 ID、交付结果与依赖，不写状态。表中的依赖引用任务 ID；图与表都只表达实施顺序，不代表不同发布版本。

## 附录：写作检查清单

提交方案前检查（按所选档位适用）:

- [ ] 背景说明了真实问题，而不是只描述想做的功能。
- [ ] 当前实现有代码或操作依据；已有方案与用户决策的沿用、替代关系已说明，冲突已解决。
- [ ] 目标和非目标都写了。
- [ ] User Stories 覆盖核心路径、失败/兼容路径和维护者视角。
- [ ] 推荐方案有明确理由；存在实质备选时已比较，没有为凑数编造不合理方案。
- [ ] 关键选型、对外契约、生成代码流程与模块边界已明确，没有把实施阻塞留成「后续确认」。
- [ ] 改动清单具体到文件 / 函数，不是「改后端」「改 UI」。
- [ ] 涉及 Ent / GraphQL 时，写了 `make generate` 与 resolver 手写部分。
- [ ] 涉及用户可见文案时列了 `en` / `zh-CN` 两个 locale 文件。
