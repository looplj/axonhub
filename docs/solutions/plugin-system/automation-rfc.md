# RFC：插件任务的并发状态与受控动作

本文征求对接口和故障语义的意见。Cache Guard 是一个使用场景：任务按间隔读取缓存指标、保存扫描游标，并在操作者批准后产生通知或暂停指定 Key。周期性运维检查也需要同样的状态协调和权限边界。

## 基于现有任务入口

现有清单 `tasks`、`onTask(ctx, run)`、Owner 管理界面和执行历史继续作为插件任务的入口。任务可定时触发或由 Owner 手动运行，执行记录包含 `runId`。当前任务按时间槽认领；已有运行时的触发可能被跳过。以当前状态为输入的周期扫描可以从持久化游标继续。运维告警与处罚按业务证据去重，幂等标识应绑定安装、规则版本、目标和观测。

如果后续确有逐周期投递需求，可在现有任务模型上单独讨论重试策略、接管语义和积压行为。首个状态接口可以按当前任务语义交付。

## 第一阶段：安装级 KV 条件写入

在现有 `ctx.kv` 命名空间内提供一个读取条目和一个条件写入接口。读取得到值及不透明的 `revision`；写入接受期望版本，`null` 表示仅当条目缺失或过期时创建。冲突返回明确结果，任务可在现有预算内重新读取，或交给下一轮。值被删除后重建时使用新的 `revision`，防止旧写入误认为值未变。现有 KV 调用维持兼容，每次写入继续受宿主的命名空间和限额检查。

这一阶段的验收包括同一版本只能由一个并发调用者更新、过期后可创建、删除重建后旧版本失败、旧条目可继续读取，以及两个安装之间完全隔离。需要维护者确认是否同时向插件页面的 GraphQL 桥开放 CAS；页面侧应继承同等权限和预算。

## 第二阶段：受控运维动作

有界、只读的指标接口提供评估输入。动作权限单独授予；直接登录的系统 Owner 为每个安装设置可访问的项目和 Key，空范围默认拒绝。后台写入在短事务内重查当前安装状态、授权、范围和运行所有权。方案沿用现有的请求授权和插件运行模型，在宿主处理动作时增加经过验证的业务入口。

通知通过已配置的宿主 Webhook 目标入队。可评审的契约包括稳定的事件 ID、可见的重试状态和投递失败处理。HTTP 投递在写入事务之后执行；接收方可用事件 ID 去重。若日后支持暂停附带通知，暂停与入队可在同一事务提交，随后独立投递。

对 Key 的暂停提议采用独立记录，叠加在管理员的人工状态上。短期暂停按宿主时间到期；独立的管理员恢复入口应能查询和解除遗留记录。首期讨论可聚焦临时暂停，永久暂停待确认恢复和故障行为后另行评审。新请求的状态码、数据库故障时的可用性取舍，以及插件撤权或卸载时如何显示遗留记录，都需要在改变网关鉴权前达成共识。

## 希望维护者确认的问题

KV CAS 是否适合作为第一个独立变更？任务只需在下一次执行时继续，还是有明确场景要求对同一时间槽重试？宿主应先提供通知队列，还是先明确自动暂停、恢复和撤权的统一边界？这些决策可分别评审，每项通过小型实现和并发、授权、迁移测试验收。
